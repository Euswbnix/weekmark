# v0.3 design — PageLamp writes plans and explanations itself (model access)

Status: **draft 3** (maintainer, 2026-09-27), with the course-calendar addendum of 2026-09-28. Replaces
the draft of 2026-09-25. It is based on four research reports of 2026-09-27: official Codex, the
student's own Claude Code, API keys (BYOK) and local models, and updater / signing / extraction
worker. Delivery order, owners and dates are in `v0.3-plan.md`. Vendor facts are as of 2026-09-27 and are cited as [n] (list at the end, all
accessed 2026-09-27). **[unverified]** marks claims that a primary source or a test must still
confirm. This space changes monthly: re-check every vendor fact when implementing it.

Draft 3 applies the review of 2026-09-27. The main changes:
- the prompt gate is now enforced by types end to end: drivers accept only a `RenderedPrompt` (§3.2, §4.3);
- a second per-course question, "may course materials be shared with an AI service", is enforced in the facade (§4.1);
- schema v3 moves into M0, and the AI tables become v4 (§5.4);
- a cross-process Codex lock, a weekly run cap and a credits disclosure for mode A (§2.3);
- a stricter budget estimate stored in micro-USD (§3.5);
- a canary test showing that course text never reaches disk (§4.4);
- reminder and startup logic moves into the facade (§5.3);
- all six Canvas §2E disclosure items are covered (§9).

**Addendum 2026-09-28.** The course calendar joins as a **fourth model feature**: the model reads a
course's syllabus and schedule and copies dates with the exact words they come from; core validates
and assembles them into a calendar the student confirms. It is the first feature to ship
(alpha.3). Its full design, together with the deterministic week fix and course removal, is
`v0.3-course-calendar.md` ("the calendar design"). This document changes only where the calendar
joins the shared layer: §0, §1, §3.1, §3.3–§3.5, §3.7, §3.8, §4, §5, §6, §7, §8, §9, §10, §11.

## 0. Decisions in one screen

1. **Four ways for PageLamp to use a model, plus the v0.1 path.** They are listed in priority order.
   - **A. ChatGPT plan through official Codex:** PageLamp downloads the official, unmodified Codex
     binary when the student turns this on. Codex signs the student in itself. **Not offered**
     (decided 2026-10-03, §2.3); the code stays switched off (`CHATGPT_PLAN_OFFERED = false`).
   - **B. Claude plan through the student's own Claude Code:** built behind a compile-time flag.
     It ships **only after Anthropic confirms in writing** (§2.4).
   - **C. The student's own API key (BYOK):** the advanced option.
   - **D. A model on this computer:** Ollama or LM Studio.
   - **Reverse MCP (v0.1)** stays the zero-setup path for every student.
2. **One provider layer, `crates/pagelamp-llm`**, written in-house. It is a closed `Backend` enum:
   HTTP drivers, Codex exec, and Claude Code headless. It sits behind the `pagelamp-app` facade,
   so Tauri, the Swift shell and the CLI all get every feature. `pagelamp mcp` never links it.
3. **The course AI policy gates every model call by type.** Course text can reach a prompt only as
   a `GatedContext`. Only `pagelamp-core::ai_gate` can build one, and it builds it from
   `AiMaterialsState` (ARCHITECTURE §3 rule 8). Drivers accept nothing but a `RenderedPrompt`,
   and only `ai_gate::assemble` can build that (§3.2). A course whose materials the student marked
   "may not be shared with an AI service" never sends material text to a **cloud** backend
   (§4.1; owner decision D37: on by default, remind, don't block — the 2026-09-25 decision).
4. **Four features; two of them send course material text.**
   - **Study plan:** the model sees structure only; dates come from a deterministic scheduler.
   - **Weekly explanation:** sends material text. Course state must be `readable`, and every claim
     is cited to a chunk.
   - **Course calendar** (addendum 2026-09-28; alpha.3): sends the text of a course's syllabus and
     schedule candidates. Course state must be `readable`; every date must quote text found in a
     material and parse from that quote; the result is a proposal the student accepts (the
     calendar design §7).
   - **Weekly progress reminders:** deterministic, no model needed. An optional AI "weekly note"
     sees structure only.
5. **Nothing leaves the machine until the student has chosen a backend and read its disclosure.**
   Every run is started by the student. Output is labelled AI-generated and stored locally. No
   chat UI, and no tools for the model in v0.3.0.
6. **Assignment rule unchanged (ARCHITECTURE §3 rule 4).** PageLamp never fetches assignment
   instructions and never helps complete or submit graded work. Prompts, context selection and
   output checks all enforce this.

## 1. Goals and non-goals

**Goals (v0.3.0)**
- PageLamp generates a day-by-day study plan, an explanation of a course week with citations, and
  weekly progress reminders.
- PageLamp reads a course's syllabus and schedule into a cited course calendar the student confirms,
  on top of a deterministic week and phase that needs no model (the calendar design).
- The student uses an API key or a local model, or, where Anthropic confirms in writing, a
  Claude plan they already pay for. A ChatGPT plan works with PageLamp through the student's own
  Codex or ChatGPT desktop over MCP (mode 0); mode A is not offered (§2.3).
- The same facade API serves the Tauri app (all OSes), the SwiftUI shell (macOS) and the CLI.
- The course AI policy is enforced in front of every model call, local models included (§4).

**Non-goals (v0.3.0)**
- A chat UI or a tutor loop. Follow-up questions and a read-only tutor come later (§11).
- Tool use by the model.
- Background or scheduled model runs. The only exception is an opt-in weekly note for backends
  that allow it (§5.3). The course calendar adds no exception (plan D47).
- Any PageLamp server, relay, proxy, resale or pooling of usage.
- Handling subscription tokens, or offering our own "Sign in with ChatGPT/Claude" screen.
- Native PDF input to models. Local extraction stays the baseline.
- Named presets for Chinese model platforms. The generic OpenAI-compatible endpoint is the most
  we offer (owner decision), and coding-plan endpoints are refused (§2.5).

### 2.3 Mode A: ChatGPT plan through official Codex

**Why exec**
- `codex exec` is labelled **Stable**. `codex app-server` is Experimental, "not supported for
  production workloads" [2][3][4].
- `codex mcp-server` was removed in 0.154.0 [1].
- Codex ships weekly (latest stable 0.157.1 on 2026-09-26) and is Apache-2.0 [1].

**Runtime: download on demand, never bundled**
- Why not bundle:
  - the binary is 240–324 MB unpacked (0.158.0: macOS arm64 240, macOS x64 258, Windows x64 324 MB; checked 2026-09-29);
  - a new stable ships every week;
  - the Linux package vendors an LGPL `bwrap` helper;
  - OpenAI's terms restrict distributing its Services [13].
- The pinned version, the SHA-256 per target, the default model per feature, a **fallback
  model per feature** and a short **list of supported models** live in a data file,
  `crates/pagelamp-llm/data/codex-pin.toml`. The maintainer bumps it at least monthly, before every
  model retirement, and out of cycle when the "newer version" error below is seen (A7's canary or
  a field report); the backend reviews.
  - GPT-5.5 retires on 2026-10-14 [10], before M2 starts, so the first pin must already default
    to a successor.
- **Observed 2026-09-28 on a maintainer's Mac:** the
  standalone Codex CLI 0.144.1 failed every run with HTTP 400 "The 'gpt-6-astra' model requires
  a newer version of Codex. Please upgrade to the latest app or CLI and try again.", because the
  account's default model had moved on; the Codex CLI inside the ChatGPT desktop app
  (0.158.0-alpha.2.1) worked. So a pinned version can stop working when OpenAI changes the
  default model, not only when it retires one. The design response:
  - **every run passes an explicit `-m`** from the pin's supported list (the student may choose
    only among those), never the account default. Whether an explicit supported model always
    avoids this error is **[unverified]**; A7's default-model canary checks it;
  - the 400 maps to `ModelErrorKind::RuntimeOutdated` (§3.4), matched on "requires a newer
    version of Codex". It is never retried. If the installed runtime is older than the current
    pin (for example, the runtime was not reinstalled after a PageLamp update), PageLamp installs
    the pinned version ("PageLamp needs a newer Codex; updating…"); otherwise the student sees
    "Update PageLamp to keep using your ChatGPT plan", and the updater check runs. PageLamp never
    downloads a Codex version that isn't in its pin, because only the pin's SHA-256 values are
    trusted;
  - the pin is refreshed on schedule and on this error (above), and plan A7 adds the canary.
- **Targets.** Pins cover the platforms PageLamp itself ships (`release.yml`: macOS arm64 and
  x64 via the universal DMG, Windows x64, Linux x64). The asset is chosen by the **running** OS
  and CPU, not by PageLamp's build target (a universal DMG on an Intel Mac needs the x64 asset).
  Windows arm64 (x64 PageLamp under emulation) gets the native arm64 asset and is labelled
  untested.
- **"Use my ChatGPT plan":**
  1. Show the download size (≈65–75 MB compressed).
  2. Download the pinned asset from `github.com/openai/codex/releases` into
     `<local_data_dir>/runtimes/codex/<version>/`. `local_data_dir` is a new
     `pagelamp_core::paths` function: `ProjectDirs::data_local_dir()`, which is `%LOCALAPPDATA%`
     on Windows and the same as `data_dir` on macOS and Linux. Today's `data_dir` is
     `ProjectDirs::data_dir()`, i.e. the **roaming** `%APPDATA%` (`crates/pagelamp-core/src/paths.rs`,
     PRIVACY.md), and two runtimes of up to ≈330 MB each plus `codex-home` must not roam.
  3. Verify the SHA-256 (GitHub asset digest and `codex-package_SHA256SUMS` [1]). On macOS, also
     check the code signature and Team ID `2DC432GLL2` (seen locally on 0.144.1). On Windows,
     check the Authenticode signature (the pinned 0.158.0 `codex.exe` is signed by OpenAI OpCo,
     LLC). Plan A7 also runs it with Smart App Control on.
  4. Keep at most two versions (the previous one for rollback).
  5. The download can be cancelled (`cancel_codex_install(install_id)`, §3.8). A partial download
     is deleted, never resumed from an unverified file.
- **Advanced (owner decision D12 in the plan):** use an already-installed `codex` whose version
  is in the tested range.

**Sign-in (Codex does it; PageLamp never touches credentials)**
- A dedicated `CODEX_HOME=<local_data_dir>/codex-home` (non-roaming; it may hold a 0600
  credential file when no keychain is available).
  - Otherwise the student's global `~/.codex/AGENTS.md`, skills and MCP servers, including the
    v0.1 `[mcp_servers.pagelamp]` entry, would leak into PageLamp runs [7].
  - The cost is a second sign-in, separate from the student's own Codex.
- Commands PageLamp starts:
  - `codex login`: browser flow, local callback on port 1455;
  - `codex login --device-auth`: beta, needs a ChatGPT security setting;
  - `codex login status`: only the exit code and the phrase "Logged in using ChatGPT" / "…an API
    key" are used; the output is never logged;
  - `codex logout`.
  - Source: [5].
- Credentials are stored with `cli_auth_credentials_store = "auto"`, i.e. the OS keychain, else
  a 0600 file inside the dedicated `CODEX_HOME` [5].
- **Never:**
  - read `auth.json` or the "Codex Auth" keychain item;
  - use `--with-access-token`, `CODEX_ACCESS_TOKEN` or the app-server `chatgptAuthTokens` mode;
  - include `codex-home/` in logs, reports or exports (a test enforces this).
- If the login mode is "API key", warn that runs bill that API key, not the ChatGPT plan.

**One run**

```
cwd  = <local_data_dir>/ai-runs/<generation_id>/     (empty; deleted after the run)
env  = cleared, then an allow-list: HOME/USERPROFILE, APPDATA/LOCALAPPDATA, SystemRoot, TMP/TEMP/
       TMPDIR, LANG, PATH, HTTP(S)_PROXY/NO_PROXY, SSL_CERT_FILE, CODEX_HOME
       (never CODEX_API_KEY, OPENAI_API_KEY, CODEX_ACCESS_TOKEN or PAGELAMP_SECRET_*)
argv = codex exec - --json --ephemeral --skip-git-repo-check --strict-config -s read-only
         -m <model from codex-pin.toml's supported list: the feature default or the student's choice>
         --output-schema <run>/schema.json
         -c features.shell_tool=false -c web_search="disabled" -c features.view_image=false
         -c features.apps=false -c features.multi_agent=false -c features.code_mode=false
         -c features.hooks=false -c history.persistence="none" -c project_doc_max_bytes=0
         -c model_instructions_file=<run>/instructions.md
stdin = the prompt (never argv): the user part of a RenderedPrompt (§3.2), then closed (EOF)
Windows: spawned with CREATE_NO_WINDOW (no console flash from the GUI app)
```

- **Config keys checked against 0.158.0 (2026-09-29).** Every key was checked against 0.158.0's
  `codex-rs/core/config.schema.json`, whose root, `[features]` and `[tools]` reject unknown keys:
  there is no `tools.view_image` (it is `features.view_image`); `features.code_mode` is a plain
  boolean; `[tools]` has only `update_plan`, `experimental_request_user_input` and `web_search`
  (tables with `enabled`). PageLamp's config.toml also turns off `unified_exec`, `js_repl`,
  `browser_use`, `computer_use`, `image_generation`, `plugins`, `collab`, `codex_hooks`,
  `plugin_hooks`, `standalone_web_search` and `memories`. The CI contract test (maintainer,
  `.github/scripts/codex-contract.sh`) loads the generated file with `--strict-config` and compares
  every `[features]` key with `codex features list`. **Open (2026-09-29):** on the ChatGPT app's
  0.158.0-alpha.2.1, `unified_exec` stayed effectively on despite `false`, and `codex_hooks`,
  `collab` and `web_search` are accepted but not listed; the contract test settles it for the
  pinned 0.158.0, and "no shell tool in `codex exec`" must hold before M2 ships. Codex also keeps
  SQLite files (logs, memories, state) in CODEX_HOME: the canary test covers them.
- **Code mode and the model catalog (2026-09-29).** In 0.158.0 `unified_exec` is forced on on purpose but
  only selects the exec backend; `features.shell_tool=false` removes every shell tool. The real gap:
  0.158.0's bundled models.json sets `tool_mode: "code_mode_only"` for all four pinned models, and the
  model catalog wins over `features.code_mode`, so the model would get code mode's `exec`/`wait`. PageLamp
  therefore sets the documented `model_catalog_json` to a file in CODEX_HOME holding those models' entries
  copied verbatim from 0.158.0 (Apache-2.0, attributed), with only `tool_mode = "direct"` and
  `shell_type = "disabled"` changed (a test diffs it against the originals). This is configuration through
  a documented key; the Codex binary stays unmodified. A7 must confirm that the models work in direct mode
  and that a signed-in session keeps the local catalog; if a model refuses direct mode, the maintainer decides
  between another model and a no-tools code mode. The exec driver's tripwire kills a run on any JSONL item
  type outside 0.158.0's benign allow-list.

- **Stdin is always closed.** `codex exec` reads an open stdin even when the prompt comes another
  way (piped input is appended to a positional prompt) and waits for end of input: spawned without
  a prompt on stdin and with stdin left open, it printed "Reading additional input from stdin..."
  and waited (observed 2026-09-28). The exec driver writes the prompt and closes the pipe; every other Codex
  command PageLamp starts (`login`, `login status`, `logout`, `--version`, the contract test's
  `exec --help`) gets a null stdin (`Stdio::null()`, the same as `</dev/null`). The M2 DoD tests
  it with a fake `codex` that waits for end of input.

- **Config file.** PageLamp rewrites `<CODEX_HOME>/config.toml` (while holding the lock below)
  with the same keys, plus:
  - `cli_auth_credentials_store = "auto"`;
  - `check_for_update_on_startup = false` (PageLamp's updater moves the pin);
  - `feedback.enabled = false`;
  - `project_root_markers = []`, so Codex treats the empty run directory as the project root and
    doesn't search parent directories for `.codex/` or AGENTS.md [6];
  - `[windows] sandbox = "unelevated"`;
  - `analytics.enabled` per owner decision D11.
  - The keys are from [6]; re-check them for each pinned version.
  - System and managed config layers still load: "User and system layers remain separate and
    still load" [6]. So the contract test asserts that no MCP server starts and no tool item
    appears.
- **Cross-process lock.** The desktop app, the CLI (`pagelamp explain`) and the Swift shell share
  one `CODEX_HOME`. Codex refreshes ChatGPT tokens itself during use [5]; how token rotation behaves
  under two concurrent runs is **[unverified]**. So PageLamp holds an advisory lock file
  `<CODEX_HOME>/pagelamp.lock` (the same pattern as `sync.lock`) around each config rewrite + run,
  and around login and logout. A second process gets `Busy`, never a parallel run.
- **No `-o` file.** The final message is taken from the JSONL `agent_message` item, so no
  course-derived text is written to disk by PageLamp (the canary test in §4.4 checks this).
- **Tripwire.** If the JSONL shows a `command_execution`, `file_change`, `web_search`,
  `mcp_tool_call` or `collab_tool_call` item, PageLamp kills the run, discards the output and
  reports `bad_output` [2].
- **One Codex run at a time** (the lock above; a queue inside one process). **Cancel** = SIGINT,
  then kill after 3 s (TerminateProcess on Windows).
- **Errors.** exec errors are plain strings [2]. They are mapped heuristically to
  `ModelErrorKind` values: `usage_limit`, `not_signed_in`, `model_not_found`, `context_too_long`,
  `runtime_outdated` (the "requires a newer version of Codex" 400 above).
  Stderr may echo course text, so only the classified code and the stderr length are logged,
  never the text.
- **Retired model.** On `model_not_found` for a pinned default, retry once with the pin's
  fallback model, so a retirement doesn't break mode A until the next PageLamp release. A live
  model list is used instead if Codex exposes one through a Stable interface **[unverified]**.
- **Weekly run cap and usage.** Mode A has no money budget, but runs past the plan limit may draw
  ChatGPT credits (below). So there is a weekly cap on PageLamp's mode A runs (proposed default:
  40 runs a week, adjustable; `BlockReason::WeeklyRunCapReached`), and every result shows its
  tokens from `turn.completed`.
- **Remaining allowance.** It isn't shown in v0.3.0; it needs the Experimental app-server
  `account/rateLimits/read` [4].
  - `CodexBackend` is a trait with only the `Exec` implementation in v0.3.0. The `AppServer`
    spike is dropped from v0.3.0 to keep M2 in two weeks (plan §3); the trait is the seam for it.
  - Switch when OpenAI marks app-server Stable.

**Disclosure specific to this mode** (the facts come from `ai_status()`, §3.8)
- Plus/Pro conversations may be used for training unless the student turns training off [9].
- A ChatGPT Edu or Enterprise workspace logs local Codex use in its Compliance API, so the
  university's admins can see prompts built from course material [9]. The UI shows the plan type
  when known, and this warning.
- **Credits.** "After you reach your included limits, available credits let you continue
  working" [8]. Codex for Students credits "can then extend Codex usage beyond the limits
  included in your plan", and OpenAI applies them to the account once verification succeeds [11].
  The disclosure says: "Past your plan limit, runs may use your ChatGPT credits." Whether `codex
  exec` draws credits automatically, without a prompt, is **[unverified]**. Plan A7 checks it and
  records the limit message text.
- Free/Go: the pricing page lists Codex for Free/Go only "in the desktop app, subject to rollout"
  [8]. Whether `codex exec` works on Free/Go is **[unverified]**, and so is whether Codex for
  Students credits (US/Canada, $100 = 2,500 ChatGPT credits, for Free, Go, Plus or Pro accounts)
  unlock it [11]. The maintainer tests this (plan A7).

**What OpenAI's documentation says** (OpenAI's position on this use is not public; asked in
writing, plan A6)
- The pricing matrix lists "Codex SDK, `codex exec`, and scriptable workflows" for Plus, Pro,
  Business and Enterprise/Education (captured 2026-09-27) [8]; OpenAI also describes building on
  the Codex harness [12].
- OpenAI's guidance points automation at API keys: "Use API key authentication for programmatic
  Codex CLI workflows, such as CI/CD jobs" [5]; "API keys are the right default for automation …
  Use this path only if you specifically need to run as your Codex account" [2].
- PageLamp would use only documented interfaces and run the unmodified binary for one student on
  their own machine, only when the student asks. Whether that counts as a "programmatic
  workflow" is exactly what A6 asks.
- Constraints [13]:
  - no account sharing, and no circumventing rate limits (no retry storms, no account rotation);
  - the Usage Policies prohibit "academic dishonesty", which matches rule 4;
  - brand: label it "Use my ChatGPT plan (through OpenAI Codex)", with no OpenAI logos.
- No document explicitly allows or forbids a third-party app driving a user's ChatGPT-signed-in
  Codex. **Ask OpenAI in writing; mode A ships only with OpenAI's written confirmation** (plan
  A6). A6 quotes the two sentences
  above and asks one precise question: is a local, open-source, single-user desktop app, started
  by the student, that runs the student's own signed-in, unmodified `codex exec` on their own
  computer, an acceptable use of their ChatGPT plan, or should it use API keys?

**Decision (2026-10-03): mode A is not offered**
- PageLamp starting `codex exec` is programmatic use of the Codex CLI, and OpenAI's documentation
  directs programmatic Codex CLI workflows to API-key sign-in [5]: the no-go case below.
- PageLamp's own features already take the student's API key directly (mode C), so a
  Codex-with-an-API-key mode would add nothing.
- A student's ChatGPT plan still works with PageLamp through their own Codex or ChatGPT desktop
  over MCP (mode 0).
- The code stays switched off (`CHATGPT_PLAN_OFFERED = false`) and the ChatGPT card stays hidden.
  Whether to remove the code is decided after v0.3.0.

**Go / no-go for mode A in a release** (kept for the record)
- Go when all of these hold:
  - the owner's plan tests pass (at least Plus; Free/Go results decide the copy);
  - the CI contract test passes on the pinned version;
  - the tripwire, env-scrub, lock and canary tests are green;
  - OpenAI has confirmed in writing that this use is allowed.
- No written confirmation by alpha.3 (2026-11-22): alpha.3 ships without mode A, the code stays
  behind a switch, and it can follow in v0.3.x once OpenAI confirms.
- No-go, or pull it in the next update, when any of these happens:
  - OpenAI objects in writing or changes its terms against it;
  - **OpenAI answers A6 with "use API keys" for this case** (mode A is then removed, and the
    ChatGPT card points to API key, local and MCP paths);
  - exec loses Stable status without a replacement.

### 2.4 Mode B: Claude plan through the student's own Claude Code

**Policy status**
- Since early September 2026, Anthropic's Claude Code legal page says it does not prevent "an end
  user from signing in to the unmodified Claude Code binary with their own Claude subscription".
  It allows products that run Claude Code under the Commercial Terms, if:
  - the binary is unmodified;
  - no sign-in method is removed or restricted;
  - nobody pays for, resells or intermediates usage;
  - "Claude Code" is not used in product or feature names.
  - Source: [14].
- The same page still forbids routing requests through plan credentials "on behalf of their
  users". Enforcement "may" come without notice [14]. The subscription credit plan was paused on
  the day it was due [19].
- **This remains a gray area. Written confirmation is required before release.**

**Integration**
- **Discovery (never bundled, installed or updated by PageLamp):**
  - the path the student chose, or known install paths (native installer `~/.local/bin`,
    Homebrew, WinGet, npm) [23], or a login-shell `command -v claude` (path only);
  - on Windows, the native `.exe` is preferred over npm shims.
- **Verification:**
  - macOS and Windows: an Anthropic code signature. Linux: show the path and let the student
    confirm.
  - Version from `claude --version`; minimum ≥ 2.1.259 (proposed; for `--permission-prompts`)
    [18].
- **Sign-in state:** `claude auth status`. Only `loggedIn`, `authMethod`, `apiProvider` and
  `subscriptionType` are kept; the email and org fields are dropped at parse time. These field
  names come from community reports only **[unverified]**.
- PageLamp never starts the login itself unless Anthropic's answer allows it. It tells the student
  to run `claude` in a terminal.
- **One run** (confirm in the spike, plan A8):

```
cwd   = <local_data_dir>/ai-runs/<generation_id>/ (empty)
env   = inherited, minus PAGELAMP_SECRET_* only, plus CLAUDE_CODE_DISABLE_CLAUDE_MDS=1,
        CLAUDE_CODE_DISABLE_AUTO_MEMORY=1, ENABLE_CLAUDEAI_MCP_SERVERS=false
```

### 2.6 Mode D: local model

- **Detection.** PageLamp detects a running Ollama (`127.0.0.1:11434`) or LM Studio (`:1234`,

  - it is on a loopback URL;
  - it has no `remote_host` in Ollama's `/api/tags`;

  `num_ctx` exists only on `/api/chat` [37]. PageLamp sets `num_ctx` to fit the gated context,

  - 8 GB RAM: Gemma 4 E4B or Qwen3.5 4B;

  - Hence: explanations must stay grounded in cited chunks, and the output is labelled "on-device

**Why the gate is type-level end to end** (review blocker, 2026-09-27)
- Draft 2 let `GenerateRequest.turns` carry any text, and `GatedContext::render()` was public, so
  any code in `pagelamp-app` could have put material text into the one user turn. That would undo
  the owner's binding rule that the policy engine sits in front of every model call.
- Now:
  - `GatedContext::render()` is `pub(crate)` inside `pagelamp-core`, called only by `assemble`;
  - drivers take a `RenderedPrompt` and nothing else that carries text;
  - the template must be a `&'static str`. `pagelamp-app` denies `Box::leak` and `String::leak`
    through clippy `disallowed-methods`, so a runtime string can't be turned into a template;
  - the only other student input is a `StudentNote`, clipped to 500 characters.
- Tests (backend DoD, M1):
  - **compile-fail tests** (`compile_fail` doctests paired with positive snippets; trybuild was dropped on
    2026-09-28 because its stderr snapshots break across rustc releases): building a `RenderedPrompt` or `GatedContext` outside
    `ai_gate`, or calling `render()` from `pagelamp-app`, fails to compile;
  - a **golden test per wire**: the HTTP request body (M1), the Codex stdin (M2) and the Claude
    stdin (M4) never contain chunk text from a non-readable course (§4.4).

**Rules that follow from the vendor facts** [26][28][31][33][37]
- **Structured output falls back in three tiers:** native strict schema → `json_object` →
  prompt-only.
  - Always use the lowest-common-denominator schema: every field required,
    `additionalProperties: false`, depth ≤ 5, no numeric or string bounds, no recursion.
  - Validate locally, and repair once.
- **Anthropic 4.7+ models:**
  - never send `temperature`, `top_p` or `top_k`;
  - never prefill;
  - never force a tool as a JSON trick; use `output_config.format`;
  - Opus 5.5 cannot turn thinking off, so "Lowest" maps to effort `low` and the UI says so.
- **Effort** "Lowest" = `none`/`minimal` where the model allows it.
- **OpenAI:** `store: false` always. The quota and spend 429 codes are never retried [29].
- **Ollama:** set `num_ctx` explicitly; turn thinking off for summaries.
- **Model IDs** are never hard-coded in code. Per-release defaults live in data files, and the
  live model list plus the probe decide what the student can pick.

### 3.3 Streaming and cancellation

**Streaming**
- Drivers turn SSE, JSONL or NDJSON into `StreamEvent`s. The facade maps them to the public
  `GenEvent` stream (§3.8), which reaches each surface like this:
  - **Tauri:** `tauri::ipc::Channel<GenEvent>`, the same pattern as `SyncEvent`.
  - **Swift:** a foreign trait `GenerationObserver` (the same pattern as `SyncObserver` in
    `pagelamp-ffi`).
  - **CLI:** prints text deltas.
- Structured features (plan, note, explanation) stream stage events and usage, not raw JSON. The
  explanation is schema-constrained JSON too, shown once it is validated (every paragraph's
  citations resolved locally), not streamed as text: grounding over streaming, and mode A's
  `codex exec --output-schema` doesn't stream anyway (decided 2026-09-29).
- **Timeouts:** a generous time-to-first-byte (reasoning models can think for minutes) plus an
  idle timeout between events.

**Cancellation is an explicit API**
- `cancel_generation(generation_id)`. The caller creates the id (a UUID), so it can cancel before
  the result returns. It is implemented from alpha.3, for the course calendar, earlier than M3.
- Why explicit:
  - UniFFI 0.32 does not cancel the Rust future when a Swift `Task` is cancelled (PR 3007 was
    still open on 2026-09-24) [39];
  - a Tauri `invoke` can't be cancelled from JS either.
- The facade keeps a map `generation_id → CancellationToken`. Each backend reacts differently:
  - **HTTP drivers:** `select!` on the token and drop the stream.
  - **CLI backends:** SIGINT, then kill.
- A cancelled run records estimated usage (the conservative estimator of §3.5 applied to the
  streamed text), marked "≈".
- The same explicit-id pattern covers the other long operations: `cancel_sync()` (mac shell
  facade request F4) and `cancel_codex_install(install_id)`.

- 400/401/402/403/404/413;
- OpenAI `*_spend_limit_exceeded` and `credit_balance_exhausted` [29];
- Anthropic `enforced_spend_limit_reached` [33];
- Codex and Claude usage limits.

A mid-stream error after text was shown → "Try again" (no silent double billing).

### 3.5 Budgets, usage ledger, prices

- **Ledger.** A local table `ai_usage` holds counts only, never content: time, backend, model,
  feature, token counts by kind, estimated micro-USD, `estimated` flag, outcome. It is kept 13
  months.
- **Prices** come from a models.dev snapshot vendored at release time (MIT) [40] plus our overlay.
  There is no runtime catalog fetch: that would be a new network destination.
- **Display per mode:**
  - API key: estimated cost;
  - local: tokens and seconds at $0;
  - Claude Code: plan utilisation from `rate_limit_event`;
  - Codex: tokens from `turn.completed` usage, with no cost.
- **Money is stored as integer micro-USD** everywhere (`u64`), never `f64`: the ledger, the
  budget (`set_monthly_budget(Option<u64>)`) and the estimates.
- **Budget (API keys only).** A soft monthly cap (owner decision D18; proposed US$5). A pre-flight
  estimate blocks a run over the cap (`BlockReason::BudgetReached`), with an override. Settings
  also recommend the provider's own hard caps (OpenAI project spend limit, Anthropic spend limit,
  prepaid credits) [29][33].
- **Pre-flight estimate** (an upper bound, not "characters ÷ 4", which runs low for zh-CN text
  and code):
  - input tokens: a conservative count, 1 token per CJK character plus UTF-8 bytes ÷ 3 for the
    rest **[estimate; tune against recorded usage]**, or the provider's own free token-count
    endpoint where one exists;
  - plus `max_output_tokens`;
  - plus a reasoning allowance for models whose thinking can't be turned off (for example Opus
    5.5) or whose effort is above "Lowest";
  - × 2 when a repair call is possible (structured output tiers 2–3).
  - The UI shows "≈ $x" before Generate. `estimate_generation` (§3.8) returns it.
- **Course calendar** (addendum): about 60k characters of context per course (≈24k for local
  models), 4k output tokens, the lowest effort, a small model by default; the batch "read syllabi
  for N courses" shows the total "≈ $x" first; in mode A each course counts as one run toward the
  weekly cap **[estimate]**.
- **Unknown price.** A model released after the vendored snapshot has no price, so the cap can't
  be enforced. The first run on such a model needs a per-model acknowledgement, "the budget is not
  enforced for this model" (`BlockReason::PriceUnknownNotAcknowledged`,
  `acknowledge_unpriced_model`). Its usage is still counted in tokens.
- **Cost for a realistic month** (5 courses, ≈2.3M input + 0.15M output tokens, no caching; list
  prices [27][30][34]):

  | Model | ≈ US$/month |
  |---|---|
  | gpt-6-luna | 0.30 |
  | gemini-2.5-flash-lite | 0.29 |
  | claude-haiku-4-5 | 3.05 |
  | claude-sonnet-5 | 6.10 |
  | claude-opus-5-5 | 12.20 |
  | gpt-6-astra | 30.50 |

  The draft's "frontier ≈ $3.4" was 4–9× too low. Per-feature routing to small models is
  essential. The workload estimate predates the structure-only plan and note (§5), which send far
  fewer tokens.

### 3.6 Secrets and child processes

**Provider keys**
- Stored by `pagelamp-core::secrets`: service `dev.pagelamp`, account `llm:<provider_id>`, env
  override `PAGELAMP_SECRET_LLM_<ID>` (existing mechanism).
- Never written to the DB, logs, MCP, reports or frontend state beyond the input field.
- `remove_model_provider` deletes the keychain entry. `App::open_at_with_secrets` + `MemorySecrets`
  cover tests.

**Subscription credentials**
- Never read, stored, relayed or logged (rule 10, §10).

**Child processes** (`extract-worker`, `codex`, `claude`)
- An absolute, verified path; an empty per-run working directory.
- `PAGELAMP_SECRET_*` is never in their environment.
- Prompts go on stdin, never argv.
- On Windows, spawned with `CREATE_NO_WINDOW`.
- stdout is capped. For generation runs (`codex`, `claude`), stderr can echo course text, and
  redaction can't recognise it, so only a classified error code and the stderr length are
  logged. The extraction worker writes only error codes to stderr (its panic hook prints the
  panic location, not the message, which could quote file text), so a clipped tail is kept.
- Their output is untrusted data.

### 3.7 Concurrency

- **Short store work, never across an `.await`.** Building a context is a read in
  `spawn_blocking`, and the connection is released before the model call. Results are written in
  one short read-write transaction with `busy_timeout` (ARCHITECTURE §4).
- **No lock between generation and sync.** Generation doesn't take `sync.lock`. A sync running
  during a generation only means the manifest may be stale (§5.2).
- **Concurrency limits:**
  - at most one generation per feature (and per course/week) at a time, and at most one course
    calendar run per course; a second request → `busy`;
  - Codex and Claude Code runs are serialised **across processes** by a lock file (§2.3, §2.4),
    and queued one at a time inside a process.
- **Updates don't kill running work.** On Windows the app "is automatically exited when the
  install step is executed" [44]. So `activity()` (§3.8) reports running syncs, generations and
  Codex installs; the UIs disable "Install and restart" while any runs and offer to cancel them;
  the Tauri `on_before_exit` hook waits (bounded) for cancellation to finish.

## 4. The course AI policy gate

### 4.1 What each course state allows

| `AiMaterialsState` (computed, rule 8) | Study plan (structure) | Weekly explanation (text) | Course calendar (text; addendum) | Reminders (deterministic) | AI weekly note (structure) |
|---|---|---|---|---|---|
| `readable` (policy unknown / learning_aid / allowed_with_citation / unrestricted, switch on) | yes | yes; on a cloud backend per question (b) below | yes; on a cloud backend per question (b) below | yes | yes |
| `turned_off` (student's switch off) | yes, structure only | no: `CourseAiTurnedOff` | no: `CourseAiTurnedOff` (the deterministic scan still works) | yes | yes, structure only |
| `withheld_by_policy` (`ai_policy = prohibited`) | yes, structure only | no: `CoursePolicyProhibited` | no: `CoursePolicyProhibited` (the scan still works) | yes | yes, structure only |
| hidden course | no (excluded) | no: `CourseHidden` | no: `CourseHidden` | no | no |

**What each part means**
- **Structure** = titles, kinds, dates, week numbers, deadlines, counts and the plan's own items.
  This is the same definition as rule 8, so planning stays available for every visible course.
  A course calendar's dates, break kinds, phase and week numbers are structure; its break labels,
  week topics and quotes are **material text** and never appear in structure-only contexts,
  notifications or MCP output (the calendar design §7.11).
- **Local models are gated too** (recommended; owner decision D17). A "No AI" course rule doesn't
  depend on where the model runs.
- **Two questions per course, not one** (review of 2026-09-27; owner decision D37, option 2,
  2026-09-25).
  - (a) **"Is AI use allowed in this course?"** This is the existing `ai_policy`
    (`unknown` / `learning_aid` / `allowed_with_citation` / `unrestricted` / `prohibited`).
  - (b) **"May this course's materials (slides, notes) be shared with an AI service?"**
    `MaterialSharing` = `unanswered` / `allowed` / `not_sure` / `not_allowed`, set with
    `set_course_material_sharing`.
  - Why (b) is separate: UofT's student guidance says "Avoid uploading or sharing content that
    belongs to your instructors without their permission. This includes lecture notes…" [46].
    UofT's "no outside assistance … unless otherwise specified by your instructor" default is
    written for marked work [47]. For a weekly explanation, the material-sharing rule is the
    stronger one. Canvas API Policy §3(k) also prohibits use that "you know or reasonably should
    know violates the policies … of Instructure's customers" [48].
- **Enforced in the facade, not the UI**, so the CLI and the Swift shell can't skip it. For a
  weekly explanation or a course calendar on a **cloud** backend (modes A, B, C, and cloud models
  in mode D):
  - **Decided: D37 option 2, the owner's 2026-09-25 decision** ("AI access on by default; one
    disclosure; a nudge, not a block"; the maintainer restored it after the review recommended option 1):
    - `unanswered` / `not_sure` → proceed. The course's first cloud run (an explanation or a course
      calendar, plan D49) shows a one-time, non-blocking reminder ("Check whether your instructor
      allows sharing course materials with AI services") with the three answers inline, and the
      result card notes that material text was sent to the named service;
    - `allowed` → proceed;
    - `not_allowed` → `BlockReason::MaterialSharingNotAllowed`: nothing is sent to a cloud
      backend; PageLamp offers an on-device model or a structure-only overview instead.
  - **D37 option 1 (stricter, the review's recommendation; not taken):** nothing is sent until
    the student answers `allowed`; `unanswered` asks first and `not_sure` behaves like `not_allowed`. It
    asks before the first cloud explanation of every course [46]. Option 2 was chosen instead.
  - The binding "AI access on by default" stays: materials remain `readable`, local models and
    structure-only plans are unaffected, and so is reverse MCP (the student's own AI app, v0.1
    behaviour). The owner may revisit D37 after UofT answers the owner's note (plan A14).
- **Policy wording.** `allowed_with_citation` adds "cite AI use per your course rules" to the
  explanation footer. `unrestricted` changes nothing else: rule 4 still applies.

### 4.2 `GatedContext`

```rust
// pagelamp-core::ai_gate — no network, no model; the only producer of prompt-bound course data

pub fn calendar_context(store: &Store, course: &str, at: AsOf, budget: ContextBudget) -> Result<GatedContext>; // addendum: Blocked unless
                                                        // readable; syllabus/schedule candidates + a structure block (calendar design §7.3)
impl GatedContext {
    pub(crate) fn render(&self) -> String;              // blocks wrapped as <course_material id="c12" title=… locator=…>;
                                                        // only ai_gate::assemble calls it (§3.2)
    pub fn summary(&self) -> ContextSummary;            // courses used + their state, materials included/trimmed/left out (no text)
    pub fn resolve_citation(&self, handle: &str) -> Option<CitationTarget>;
    pub fn manifest(&self) -> &ContextManifest;         // material ids + content_hash + chunk ords (for staleness)

```

**How the gate works**
- State is read **inside the same read transaction** as chunk selection. No state is cached
  across calls: it is computed, never stored.
- Text comes only from `chunks` of courses that are `readable` at that moment.
  `withheld_by_policy` and `turned_off` courses contribute structure only, and hidden courses
  nothing.
- **Left out by default** (listed in `ContextSummary.left_out` with a reason, shown in the UI):
  - materials that look like assessments. Decided by source first (a material whose only module
    or folder context is an assignment or quiz item, where the sources record it **[check what
    `pagelamp-canvas` stores]**), then by title (assignment / homework / HW / problem set / quiz /
    exam; tunable, **open item**). Titles like "Midterm review" or instructor-posted "practice
    solutions" are no longer dropped on one word alone. Every left-out item has a one-click
    "include";
  - `external_link` materials;
  - materials without text.
- **Budget:**
  - ≤ 50% of the model's context window, capped per feature (explanation starting value ≈ 200k
    characters);
  - for Ollama, `num_ctx` is sized to fit, and a smaller cap applies;
  - each material gets a fair share; trimmed materials are listed.

### 4.3 Prompt assembly and injection defence

**What a prompt contains** (all built by `ai_gate::assemble` into one `RenderedPrompt`, §3.2)
- Fixed instructions come from `prompts.rs` (a `&'static str`): the four core rules from
  `ai_rules`, the feature task, and the output schema.
- Then the rendered `GatedContext`.
- Then, optionally, the student's own note ("focus on the midterm") as a `StudentNote`: clipped to
  500 characters and wrapped as data.
- The output language is a parameter: a setting, "course language" or "UI language" (default UI
  language).
- There is no other input path, and the types enforce it.

**Defences against instructions hidden in course text**
- No tools in any run (enforced by Codex tripwire, Claude `--tools ""`, and empty HTTP `tools`).
- Material wrapped in tags with a "data, not instructions" rule.
- Schema-constrained output.
- Citations must resolve to handles in the context: unknown handles are dropped and counted, and
  too many drops → `bad_output`.
- Course calendar (addendum): every date must quote text that is found in the material, and the
  date must parse from that quote; there is no repair retry for invented quotes; conflicts between
  claims are shown to the student, never resolved silently (the calendar design §7.5, §7.7).
- Output is only ever displayed or stored after the student accepts it. It never triggers an
  action.
- Output is rendered as a Markdown subset with no raw HTML. Links open only `http(s)` URLs through
  the opener, never automatically.

## 5. Features

### 5.1 Study plan

**Inputs** (`StudyPlanRequest`)
- Horizon: default 14 days, maximum 56.
- Study hours per week: default 10.
- Days off: weekdays.
- Courses included: default all visible, active courses (active = the course lifecycle's
  `is_active`: Current, Finishing, Unknown, or Upcoming within 14 days; the calendar design §8.1).
- An optional note.

**How it works**
1. **Deterministic anchors** (`pagelamp-core::planner`):
   - deadlines and exams from `list_deadlines`;
   - each course's `default_week` and phase (timeline) and its materials for this week and next
     (ids and titles); in a break the plan favours catch-up and review, in the exam period exam
     preparation;
   - daily capacity = hours ÷ study days, capped at 4 h a day.
2. **Model step (structure only).** The model returns tasks
   `{course_ref, kind: read|review|practice|prepare_deadline|catch_up, title, description,
   material_ids, minutes, priority, earliest, latest}`.
   - The prompt forbids tasks that produce graded work. For example: "Start A2 (due Oct 14):
     re-read week 4 slides" is fine; "Write A2's answers" is not.
3. **Scheduler places the tasks:**
   - by `latest` and priority, within capacity;
   - reviews before exams, work spread before deadlines;
   - anything it can't place goes to `unscheduled`, with a reason.
4. **Validate** with the existing `validate_study_plan` limits (200 items, 300-character titles,
   4,000-character text, 50 material ids). `material_ids` must be in the manifest; unknown ids
   are dropped.
5. The result is a **draft**: `GeneratedStudyPlan { meta, plan: StudyPlan, unscheduled,
   warnings }`. The student reviews it; `accept_study_plan` saves it to `study_plans` with
   `origin = pagelamp`.

**Tracking progress**
- `set_study_plan_item_done` ticks items. That feeds the weekly progress reminder.

### 5.2 Weekly explanation

**Inputs:** a course and a week (default: the course's `default_week`; during the exam period
there is no default and the student picks). The course must be `readable` (§4.1).

**Output:** `WeeklyExplanation`, containing:
- `meta`, `course_id`, `week`;
- `sections: [{heading, body_markdown, citations: [{handle, material_id, title, locator, url}]}]`;
- `check_questions` (2–3);
- `left_out`;
- `stale: bool`.

This mirrors the v0.1 MCP `weekly_review` prompt (explain in order, cite "Title, locator", then
check understanding).

**Grounding**
- Every paragraph needs at least one citation handle, and the handles are resolved locally.
- For on-device models the answer stays close to the chunks, with thinking off and a lower-quality
  label (§2.6).

**Staleness**
- If any material in the manifest has changed its `content_hash`, or new materials appeared that
  week, the result is marked `stale`: "materials changed since this was written — regenerate?".
- It is also `stale` when an accepted course calendar moved the week's start
  (`generations.week_starts_on` no longer matches).

**Kept:** the last 5 per course and week. They are deleted with the course (FK cascade) or by
`delete_generated`.

### 5.3 Weekly progress reminders

**Deterministic, with no model**
- `weekly_digest()` per visible course:
  - for active courses (§5.1): the current week, its confidence and the phase ("Reading week —
    catch up"), and this week's materials (count and titles);
  - for every visible, not removed course, whatever its lifecycle: deadlines in the next 7 days;
  - plan progress for last week (items done / planned) and today's plan items.
- `reminders(from, to)` yields three kinds:
  - `deadline_soon` (48 h and 24 h before), for every visible, not removed course; never filtered
    by the course lifecycle, so a course wrongly judged finished still reminds;
  - `weekly_digest` (default Monday 09:00 local);
  - `plan_today` (off by default).
- Each reminder has a stable id, a **local wall-clock time plus an IANA time zone** (not only an
  absolute instant) and a derived `fire_at`. Notification text uses titles and codes only, never
  material text.
- Time handling: "Monday 09:00" stays 09:00 local across a DST change. Canada leaves DST on
  2026-11-01 [49], during the alpha/beta, so a DST-crossing test is part of the M3 DoD.

**Delivery** (the logic is in the facade: `due_reminders(now)` does the catch-up window, dedupe
and maximum age; `startup_tasks(now)` says what to do at launch; §3.8)
- **Onboarding makes reminders work by default.** Reminders only fire while PageLamp runs, and
  Tauri can't schedule desktop notifications. So onboarding asks one explicit question: "Remind
  me (keep PageLamp in the tray / menu bar and start it at login)". Yes turns on both the tray and
  autostart; No leaves both off, and reminders then show only at launch (catch-up), as a card
  inside the app. That answer is also the consent for system notifications: PageLamp shows none
  until the student says yes (in onboarding or Settings), and then sends one "Reminders are on"
  notification, which is when an OS permission prompt, if any, appears (decided 2026-09-29).
- **Tauri:**
  - a Rust timer (every 15 min and on resume) calls `due_reminders`;
  - catch-up on launch comes from `startup_tasks`;
  - `mark_reminders_shown` prevents repeats.
- **Swift:** schedules `UNUserNotificationCenter` requests from `reminders(now, now + 7 days)` with
  **calendar triggers** built from the wall-clock time and time zone (not absolute dates), and
  reschedules after each sync and plan change (mac shell M3).
- **CLI:** `pagelamp remind` prints the digest and due reminders (cron-friendly).

**Optional AI weekly note**
- "Write my weekly note": 3–5 sentences plus the top 3 focus items, built from `note_context`
  (structure + progress) only.
- Started by a click. An opt-in "prepare it when I open PageLamp on Monday" is allowed for modes
  C and D only (the student's own API key, local models); modes A and B get it only after the
  vendor explicitly agrees (decision D27). The facade
  decides it (`startup_tasks`), so every surface behaves the same.

### 5.4 What is stored locally (schema v3 in M0, v4 in M1; both additive)

**Schema v3 (M0, ships in alpha.1)**

| Table / column | Content | Retention |
|---|---|---|
| `materials.text_error_kind` | extraction worker failure class | with the material |
| `materials.text_error_fingerprint` | worker protocol + app version of a hard failure (with the existing `content_hash`) | with the material |
| `schema_meta` (key → value) | `min_reader_version` | permanent |

- **Reader rule (new in v3).** `Store::open_read_only` (MCP) accepts a `user_version` newer than
  its own `SCHEMA_VERSION` if `schema_meta.min_reader_version ≤ SCHEMA_VERSION`. Writers
  (`Store::open`) still refuse any newer version with `SchemaTooNew`. Today both refuse
  (`checked_user_version`, `crates/pagelamp-core/src/store.rs`, `SCHEMA_VERSION = 2`).
  `upgrade_existing` follows the same rule.
- **Typed errors.** `AppErrorKind::SchemaTooNew` and `AppErrorKind::SchemaTooOld` (mac shell facade
  request F1; decided 2026-09-28 so the UI branches on the kind, never on the message) replace
  today's untyped `Internal`, so every surface can say "this data was written by a newer PageLamp —
  update" or point at the pre-migration backup. Over FFI both map to one `Schema` case until the
  Swift side splits it.
- **Backup before every migration.** Before migrating from version N, copy the database to
  `pagelamp.db.v<N>.bak` with SQLite's online backup (or `VACUUM INTO`, which is safe under WAL).
  Only the newest backup is kept. It contains course text, so PRIVACY.md lists it and
  `remove_all_ai_data` / "delete my data" remove it. It makes a manual downgrade possible (the
  "bad release" runbook, plan M0.7).
- **Extraction failures don't loop.** Today `is_indexed` skips only `TextStatus::Ok`
  (`crates/pagelamp-core/src/ingest.rs`), so a file that timed out would be re-extracted on every
  sync. v3: a file whose (`content_hash`, worker protocol, app version) match a stored hard failure
  (`timed_out`, `cpu_limit`, `memory_limit`, `crashed`) is skipped until one of the three changes.

**Schema v4 (M1): the AI tables**, with `min_reader_version = 3`, so a still-running v3 MCP process
keeps working after the update.

| Table / column | Content | Retention |

### 5.5 Course calendar (addendum 2026-09-28)

Summary; the full design is `v0.3-course-calendar.md`.
- **Why.** Canvas can report a term much wider than the classes (UofT's "Fall 2026" runs May to
  January), so v0.1 counted "Week 22" in September. Past courses kept syncing because professors
  never concluded them.
- **Deterministic first (alpha.1).** Enrollment-window terms are not used to count weeks; week 1 is
  fitted from the week numbers and publish dates of the professor's materials; phases (teaching,
  break, exams, ended) and a lifecycle per course; finished courses grouped under "Past". No model.
- **AI reading (alpha.3).** `calendar_context` (§4.2) sends the course's syllabus and schedule
  candidates; the model returns flat date claims with verbatim quotes (`CalendarExtraction`, the
  calendar design §7.4); core validates them (quotes must exist, dates must parse from the quote,
  years inferred from the syllabus itself, consistency, cross-checks with the materials) and
  assembles a proposal. The student accepts, edits or dismisses it. The same validator serves a
  deterministic syllabus scan (no model) and, from beta.1, proposals from the student's own AI app
  over MCP (plan D48).
- **Gate.** The same as the weekly explanation (§4.1), local models included (D17); question (b)
  per D37 option 2, with the reminder at the course's first cloud run (D49).
- **Started by the student only** (D47): sync and `startup_tasks` offer a run, never start one.
- **Removal** (alpha.2) is deterministic: a tombstone hides the course at once, sync skips it, the
  data is purged after 7 days, files go to the Trash, folder-source files are never touched.

## 6. MCP interplay

**The two paths**

| | Student's AI app over PageLamp MCP (mode 0) | PageLamp calls a model (modes A–D) |
|---|---|---|
| Who calls the model | the AI app, under the student's account | PageLamp (`pagelamp-app` / CLI), under the student's account/key/device |
| What is sent | whatever the app reads through tools; text only for readable courses | only the gated context of one feature |
| Network from `pagelamp` | none (`pagelamp mcp` never touches the network or links `pagelamp-llm`) | the chosen provider only |
| Output | in the AI app's chat; plan saved via `save_study_plan` | stored locally, labelled, shown in PageLamp |

**How they connect**
- **Shared plans.** Both paths write to `study_plans`. `get_study_plan` (MCP) and the app show the
  origin: "saved by your AI app" / "made by PageLamp with <backend> · <model>". MCP tool inputs
  are unchanged in v0.3.0. Outputs gain fields (course phase, lifecycle, the resolved teaching
  dates in `course_overview`), and plan D48 adds one prompt (`course_calendar`) and one write tool
  (`propose_course_calendar`, proposals only, refused for non-readable courses; the calendar design
  §7.9, §7.13).
- **Explanations over MCP.** They are not exposed in v0.3.0. Exposing them later would need a read
  tool that re-checks `ai_materials` at read time (open item).
- **No MCP inside PageLamp runs.** Codex runs use a dedicated `CODEX_HOME` with no
  `mcp_servers`; Claude runs use `--strict-mcp-config`. The later tutor mode may attach PageLamp's
  own MCP server read-only: allow-listed read tools, `default_tools_approval_mode = "approve"`, no
  `save_study_plan`. Codex honours the server `instructions` field [45]. Its estimates and
  budgets must count tool-output tokens (next item).
- **MCP output size (observed 2026-09-28).** With PageLamp's MCP server added to the owner's
  Codex (mode 0), one question ("where is each of my courses this week?", 13 courses) made Codex
  call `sync_status`, `list_courses` and `course_overview` ×7, and used about 113k input tokens
  (89k cached) and 1.3k output tokens. Every tool call is another model turn over the whole
  conversation so far, so tool outputs are paid for many times from the student's plan. Hence:
  - keep `list_courses` and `course_overview` compact: the v0.3 output fields (phase, lifecycle,
    resolved teaching dates) are enums and dates, never evidence prose or material text;
  - check output size on a synthetic 13-course fixture when these outputs change (the threshold is
    set at implementation **[estimate]**);
  - any PageLamp run that attaches the MCP server (the later tutor mode) counts tool-output tokens
    in "≈ $x" and the budget, and shows them in its tokens per run.
- **One binary.** `pagelamp` stays one binary: `mcp` (network-free), `extract-worker` (hidden),
  and the CLI. Startup of `pagelamp mcp` stays lightweight (ARCHITECTURE §4).
- **Complements for Claude subscribers** (zero-risk, v0.3):
  - a skills-only PageLamp plugin;
  - a documented Claude Desktop local scheduled task that calls PageLamp's MCP tools (Desktop ≥
    1.1.5368; runs only while the app is open) [24];
  - `.mcpb`, generated at runtime once signed releases exist: plan M5 if owner decision D30 says
    yes, otherwise v0.3.x. `mcpb sign` output is currently rejected by Claude Desktop [25].
  - Publishing the plugin to a public directory makes PageLamp more visible to Instructure and
    universities. Record the Canvas §3(i) reading first (§9).
